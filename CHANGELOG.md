# Changelog

## 0.5.0: free and open source, Linux, auto-lock (2026-11-05)

The user-facing notes are in `docs/RELEASE-NOTES-0.5.0.md`. Downloads and checksums are on nakos.org and in this repository's v0.5.0 release.

### Changed
- **Free for everyone.** The one-wallet limit and the license check are gone (`commands/license.rs`, `license-dialog.tsx` and the `nakos-license` dependency removed). Settings has "About Nakos" in place of the License card: version, MIT license, View source, Report a security issue, and an optional "Support development" link. A license stored by 0.4.0 stays in the database as an unused preference and is never read.
- **Any lock forgets "Remember".** Locking, by the button or the timer, removes the passphrase from the OS keychain and turns the helper off (`forget_remembered_passphrase`). Remember now means: reopen without asking after a restart, while the session is still unlocked. Someone who never opted in never has the keychain touched.
- Settings → Vault and the unlock screens describe the auto-lock in place of "there is no automatic lock".

### Added
- **Auto-lock** (`commands/autolock.rs`). The vault locks after inactivity: Off, 1, 5, 10, 15, 30 or 60 minutes, default 10 on desktop and 5 on a phone. On Android it also locks 30 s after the app leaves the screen. The clock runs in a Rust watchdog thread, so it works while the window is minimised or the webview is throttled. It counts on both the monotonic and the wall clock, so a phone that slept still locks. Activity reports check the deadline before they count, so late activity can't rescue an expired session. On lock the webview drops every cached query (`queryClient.clear()`).
- **Linux**: AppImage, .deb and .rpm bundle config; `scripts/build-linux.sh` and `scripts/linux.Dockerfile` (Ubuntu 22.04 base); README build instructions for every platform.
- **Public-release files**: `LICENSE` (MIT), `SECURITY.md`, `CONTRIBUTING.md`, and `scripts/secret-scan.sh`, which checks the tree and the whole history, with private infrastructure patterns kept in the untracked `.secret-scan.local`. The run on 2026-11-05 found nothing.
- **Signing scripts**: `scripts/sign-macos.sh` (Developer ID, hardened runtime, notarytool, stapler) and `scripts/sign-windows.ps1` (Authenticode with an RFC 3161 timestamp), with `docs/SIGNING.md`. Hardened runtime is on in `tauri.conf.json`. Neither platform is signed yet.
- **Family letter in sections**: what this is, what you need to do, where things are kept (blanks to fill in by hand), what never to share, what this letter does not contain, what you will see. Three templates: simple family, single-sig cold storage, technical multisig (one line per signing device, and "2 of the 3"). All of them import the same way.
- **Advanced packet**: "What this packet does not contain", plus structured recovery details per wallet (type, where the descriptor/xpub is, hardware model(s), numbered next steps).
- **PDF export** of the letter and the packet (`commands/pdf.rs`): a small built-in writer with standard fonts, A4, wrapping, a footer on every page ("Watch-only. Contains no seed words or private keys.", page n of N). No new crate.
- **Import guide** (`modules/onboarding/import-guide.tsx`): where to find the descriptor or xpub in Sparrow, Electrum and hardware wallets, why descriptors are better, how to tell public from secret, and an import checklist. Shown in the Today and Portfolio empty states and from "Where do I find this?" in Add wallet.
- **Seed and WIF guard**: a pasted seed phrase (12 to 24 words) or WIF private key is refused in Rust (`refuse_private_key_material`) like an xprv. The Add wallet box warns at once and never sends it to the detector (`lib/key-guard.ts`).

### Tests
- `cargo test`: 217 passed, 1 ignored, plus the integration tests. New: auto-lock deadlines and clocks (8), lock forgets Remember (1), link allow-list (1), seed/WIF guard (1), letter templates and packet recovery details (2), PDF structure, wrapping and footer (5), PDF export end to end (in the file round-trip test). `npx tsc -b` clean. `npm run test:ui`: 15 passed (key guard: 2 new).
- Fixed before release: a lock now always reaches the window even when the OS keychain fails while forgetting "Remember" (`commands/autolock.rs`, with a test). `cargo test --release` also passes on Linux (218).
- Release builds, checked by hand: macOS (Gatekeeper, backup restored into an empty vault), Windows 11 in a virtual machine (installed over 0.3.0, auto-lock), Android on a Pixel 7a (installed over 0.3.0, the 30-second background lock) and on the emulator. The Linux AppImage starts on Ubuntu 24.04 but has not been used on a Linux desktop yet.

### Added
- **License, checked offline.** Nakos is free for one wallet. A license (21,000 sats, paid once at nakos.org over Lightning or on-chain, no account) lifts the limit on every device and for every later version. The key (`NAKOS1-…`) is an Ed25519 signature over a 22-byte payload, checked against the public key built into the app (`pay/nakos-license`, key id 1 `e9f2bb17…7440`); nothing is sent anywhere. It is kept as the `license` preference, so encrypted backups carry it, and it is verified on every read, so a preference written any other way never unlocks.
  - Adding a second active wallet, or unarchiving one, needs a license (`commands/license.rs`, enforced in `add_wallet`, `add_multisig_wallet` and `archive_wallet`). Wallets already present are never hidden or locked. Importing an inheritance packet is not limited.
  - Settings has a License card (add, show the short id and issue date, remove); the welcome screen has "I have a license"; Add wallet says so before you type when the free limit is reached.
- **Recovery codes**: each invoice carries `NKS-XXXX-XXXX-XXXX` as its BTCPay order id, so it shows in the buyer's wallet history (Lightning description, on-chain label) and finds the license again on the Buy page.
- **Selling** (outside the app, in a separate service that is not part of this repository): it creates BTCPay invoices and signs licenses; the signing key never leaves that machine. Removed again in 0.5.0.

## 0.1.3 (2026-10-14)

Published 2026-10-14 at https://nakos.org (the owner uploaded it; the 0.1.2 DMG was removed from the site). macOS on Apple Silicon only: `Nakos_0.1.3_aarch64.dmg`, ad-hoc signed, not notarized (SHA-256 `49b7a04721fdd676e2645991586de702cd423e46b0b9765f5b71de39655966e9`).

### Fixed
- **Wallet sync froze the window.** `sync_wallet` was a synchronous command, so Tauri ran it on the main thread and the whole Electrum scan (about 10 s for an xpub wallet through a public server) blocked the app. It is now `async` and runs the unchanged sync work on a blocking-pool thread (`tokio::task::spawn_blocking`, the pattern the explorer commands use). Syncs still run one at a time, as before: each takes a shared lock in the app state on its background thread, so two syncs' write transactions cannot collide; a second sync now waits in the background instead of freezing the app. The privacy gate for public servers is unchanged and still runs before any connection. The website's known limit "Sync can pause the window" became "Sync takes a moment".

### Tests

### Fixed
- **Crash on any TLS Electrum connection.** Opening the Node page (or testing the connection, or letting the status poll run) with an Electrum server saved with TLS on aborted the app: the lockfile compiles in two rustls crypto providers (`ring` via `reqwest`, `aws-lc-rs` via `electrum-client`), rustls 0.23 will not pick one by itself, and nothing installed one, so the first TLS client panicked ("Could not automatically determine the process-level CryptoProvider"). On the main thread that panic cannot unwind and the process aborts. `rpc::ensure_tls_provider()` now installs `ring` once, at startup and again inside every Electrum connect. Adds a direct `rustls` dependency (default features off, `ring` and `std` on) only to name the provider; the lockfile gains one line and no new crates. Found during the first manual `SMOKE.md` run, on a scratch data directory. This predates the plugin removal (the TLS crates are identical in the lockfiles from before and after it). None of the earlier unit tests opened a TLS connection, so none caught it. With the release profile's `panic = "abort"`, the same panic on a background thread would also have been fatal.
- **UI freeze on the Node page.** After the crash fix, the same saved row (TLS on a plain-TCP port, which never answers a handshake) froze the window: `get_fee_estimates` ran on the main thread and waited out a 10 s Electrum timeout, retried once by the library, for each of six fee targets. Now `get_fee_estimates` uses the 3 s timeouts, stops after the first failed Electrum call, and uses a no-retry client (`ElectrumConfig::connect_once_with_timeout`, also used by the status poll). `connect()`, which wallet sync uses, is unchanged. `get_fee_estimates`, `get_node_status`, `test_node_connection`, `get_health_score` and `record_health_snapshot` are now async commands, so their network waits no longer block the window; the earlier 5 s bound on the status poll limited the wait but still ran on the main thread. Other network commands (for example wallet sync and the explorer commands) were not changed or audited for this (the two explorer commands were made async by the explorer fix below).
- **Bitcoin Core "Use TLS" did not use TLS.** The Node dialog had one "Use TLS/SSL" switch for both connection types. For Core it built an `https://` URL, but the RPC transport (`jsonrpc` 0.18 `simple_http`) only treats `https` as another default port and opens a bare TCP socket; it contains no TLS code. A Core connection saved with TLS on therefore sent its RPC password, or the cookie file's first line, as HTTP Basic auth in the clear, while Test connection showed a green check and the exported packet said ", TLS". (A Core connection with TLS off was always plain HTTP; that is unchanged.) Found in a read-only code review, not from a field report. No TLS was implemented and the HTTP crate was not swapped; the claim was removed instead:
  - The Core form no longer has the switch. It says Nakos connects to Bitcoin Core over plain HTTP, that TLS isn't supported there, and that the RPC password or cookie is not encrypted on the network (use a node on a network you trust). Electrum keeps its switch.
  - Adding or editing a Core connection with TLS on is refused ("TLS isn't supported for Bitcoin Core RPC connections. Turn TLS off for this connection.") and nothing is written.
  - Test connection refuses a TLS-flagged Core row before the password is decrypted, a cookie file is read or any socket opens, and records no successful connection.
  - `CoreRpcConfig::connect` and `connect_with_timeout` refuse a TLS config first, so the status poll, fee estimates and the health score cannot send a plain request for one either. The `https://` URL builder is gone; the URL is always `http://`.
  - Migration `0007_core_rpc_no_tls.sql` clears the TLS flag on existing Core rows, including in a restored older backup. Those connections themselves are unchanged (they were always plain HTTP). Electrum rows keep their flag.
  - The advanced packet's node list prints ", TLS" for Electrum rows only, and the packet's data block reports no TLS for a Core row. The simple family letter never listed nodes.
  - Unchanged: Electrum TLS (rustls, certificate checked). Still true: Bitcoin Core RPC has no encryption in Nakos.
- **Pasting multibyte text into Add Wallet aborted the app.** `sniff_source_type` (`bitcoin/descriptors.rs`) looked at the first four bytes of the pasted text with `&trimmed[..trimmed.len().min(4)]`, which panics when byte 4 falls inside a multibyte character (for example `a😀bc` or `日本語日`). The Add Wallet box calls it on every change through the synchronous `detect_source_type` command, which runs on the main thread, so the whole app aborted (release builds also set `panic = "abort"`). It now uses `trimmed.get(..4).unwrap_or("")`, so such text is reported as "unknown" like any other unrecognized input; real xpub, ypub, zpub, tpub, address and descriptor input is detected as before. Found in a read-only code review; a scan of the other non-test slicing found no similar spot on user text.
- **Imported or remote text could permanently break the encrypted backup.** The encrypted-backup guard scans the whole database file, so any `xprv` followed by 20 base58 characters in a plain-text column made every encrypted backup fail. Several columns took text with no check and have no edit or delete path: a packet's wallet name, cosigner label and hardware model, snapshot date, and contact fields, plus health snapshot details, which include the Core node's version and error text (Core RPC is plain HTTP, so even a network attacker could supply them). A hostile letter could leave the heir without an encrypted backup for good, and the error did not say where. Now:
  - Import checks every string a packet would store as plain text. A wallet with key-like text is skipped whole ("private key material is not stored"), nothing is written for it, and the offending name is not echoed.
  - Text in rows that can never be edited later is checked when written: a wallet's fingerprint and derivation path (only the xpub path validated them), every cosigner field, and a contact's name, relationship and contact method. Names, notes and labels stay unscanned, as decided earlier.
  - Health snapshot details are not stored if they contain key-like text; the row says the details were removed.
  - A refused backup now names the table and column that hold the text (for example `wallets.notes`, or `multisig_cosigners.label (can't be edited in Nakos)`), never the text itself.
  - Before refusing, Nakos rebuilds the database file once (`VACUUM`). Editing a note overwrites the old text, but deleting a row leaves it in the file's free space (deleting a wallet deletes its coins with their labels and notes; sync did the same to spent coins until the R3 fix below, which now keeps a coin that carries a label or note), so a coin label that looked like a key kept blocking backups after it was gone.
  - Not fixed: a database already polluted in a field the app cannot edit (a cosigner label, a contact field) still cannot make an encrypted backup; the error names the field but there is no in-app way to clear it. None is known.
- **A scan that omitted a coin deleted it, together with the user's lot, label, note and freeze flag.** After every successful Electrum scan, sync deleted each `utxos` row the scan had not reported as live (`prune_to_scan`, and an inline copy for single-address wallets). Spent coins and coins the server simply left out looked the same at that point, and the row holds the user's own data: cost-basis lot (`acquisition_cost_fiat`, `acquisition_date`), `acquisition_note`, `label` and `is_frozen`. A coin that came back was re-inserted as a new row with none of it, so a frozen coin returned unfrozen and `plan_spend` (which filters `is_frozen = 0`) could select it; cost-basis data also feeds tax readiness and the Lowest-tax planner. Found in a read-only code review; the trigger (a server that answers without an error but omits a coin: a lagging or rebuilding indexer, a hostile server, a dropped mempool coin, switching the primary server) is an inference, and the fix does not depend on it being common. Now:
  - A coin the scan did not report is **kept, not deleted, if it carries any user data** (frozen, label, lot cost or date, or note). It is marked not-live (`spent = 1`) and `unseen_since` records the time of the first scan that missed it. Every existing `spent = 0` reader therefore leaves it out: balances, tax counts, distribution, the Coins list, the health counts, the packet's balances and lots, and both planners, so it cannot be put into a PSBT.
  - A coin with no user data that the scan did not report is deleted as before, so a fully spent wallet still falls to zero.
  - A coin BDK reports as spent is marked `spent = 1` with `unseen_since` empty; the empty column is what separates "known spent" from "not seen". BDK's `LocalOutput` carries no spending txid, so `spent_txid` stays empty.
  - When a later scan reports the coin live again, the same row returns to `spent = 0` and `unseen_since` is cleared; its lot, label, note and freeze flag are untouched.
  - Both sync paths share one retire step, and the single-address path no longer has its own copy of the delete. Network behaviour and `ElectrumConfig::connect` are unchanged.
  - Migration `0008_utxo_unseen_since.sql` adds `utxos.unseen_since TEXT` (no data is changed; existing rows start empty).
  - Three privacy-input queries (address reuse, total coins, change-output exposure) had no `spent` filter and relied on spent rows being deleted; they now filter `spent = 0`.
  - No automatic expiry: a kept coin stays until a scan reports it again or its wallet is deleted. There is no Coins-page badge for not-seen coins (they are hidden from the list like spent ones); `unseen_since` is on the `Utxo` model and its TypeScript type for one later. Transaction rows are still pruned to the scan: nothing in the app writes the `label`, `category` or `counterparty` columns today.
- **Capitalized SLIP-132 private keys (`Yprv`, `Zprv`, `Uprv`, `Vprv`) were not refused.** The private-key guard listed six prefixes (`xprv`, `yprv`, `zprv`, `tprv`, `uprv`, `vprv`), but Nakos reads ten SLIP-132 public versions, including the four capitalized multisig ones (`Ypub`, `Zpub`, `Upub`, `Vpub`), so the matching private versions went unchecked. A multisig descriptor such as `wsh(sortedmulti(2,Zprv…))` passed `add_wallet` and was stored as pasted (the descriptor branch does not parse the key), and the encrypted-backup guard, which shares the list, did not see it either. Found in a read-only code review. `contains_extended_private_key` (`crypto/backup.rs`) now lists all ten private versions: mainnet `xprv`, `yprv`, `zprv`, `Yprv`, `Zprv` and testnet `tprv`, `uprv`, `vprv`, `Uprv`, `Vprv`. The version bytes were checked by encoding a key payload with each one and confirming the expected four-letter prefix. Wallet writes, packet import, the contact and snapshot checks and backup seal/open all use that one list, so all of them now refuse the four. Nothing else changed: the scan is still a known prefix followed by 20 base58 characters. Not covered: WIF keys, seed phrases, other-chain variants such as Litecoin's `Ltpv`, and rows already in a database (not rescanned; a database that already holds one of these keys now fails the encrypted backup, and the error names the field).
- **The explorer API token was not tied to a server, and could be sent in the clear.** The optional public explorer's token was kept until "Remove token" was clicked, and choosing another preset in Settings only rewrote the URL, so a token saved for one provider was sent to the next server as a Bearer header (or as `?token=` for BlockCypher). Plain `http://` URLs were accepted, so that could also go over the network unencrypted. Found in a read-only code review; not reproduced against a real server. Now:
  - Saving a token records the server it belongs to (`scheme://host:port`, new `db_meta` key `explorer_token_origin`; no migration). The token is only sent when the saved URL has that same origin; another port or scheme counts as another server.
  - A token is only sent over https, or over plain http to this computer (`localhost`, `127.0.0.0/8`, `::1`). Plain http to a LAN address with a token is refused. Explorer requests that carry no token can still use http, as before.
  - Saving refuses, and writes nothing, when the stored token belongs to another server than the URL being saved and the save neither replaces nor removes it; the message names the stored server, never the token. It also refuses a new token over disallowed http and a token with no server address. Turning the explorer off never needs the token sorted out. The token is encrypted before anything is written, so a refusal or a locked vault leaves the stored settings as they were.
  - Every explorer request re-checks this, so a token that may not go to the saved URL stops the request with a visible error before any HTTP.
  - A token saved before this change has no recorded server, so it is not sent until it is entered again (Settings says so). It was not bound to the current URL, because that is the situation being fixed.
  - Settings shows which server the stored token is for. `get_explorer_settings` returns `token_origin`.
  - Redirects are unchanged: `reqwest` 0.12.28 already drops the `Authorization` header on a redirect to another host or port (checked in its source). BlockCypher's `?token=` is only on the first request. Not covered: IPv4-mapped IPv6 loopback (`::ffff:127.0.0.1`) is treated as non-loopback, so a token is refused for it; the Core password and cookie are unchanged (Core RPC is plain HTTP, see the Core TLS entry).
- **Consolidation paid to an address that already held coins, with no key origin on the output.** `plan_consolidation` asked for an unused address, but sync only stores addresses that received coins, so none ever existed and it fell back to the most recently seen address: a reused address. The output was also built with no key origin, so a signer showed it as an external send instead of change. Found in a read-only code review. Now the destination is chosen the way change is chosen in `plan_spend`: a stored unused change-chain address, else the next change address derived from the wallet's change descriptor (one past the highest change index sync has seen), else a stored unused receive address; with none of those, planning is refused ("no unused address to consolidate into ... Nakos will not pay a consolidation to an address that already holds coins"). The destination output carries its key origin, and a destination without one is refused. Wallets that cannot consolidate now get an error instead of a reused address: no change descriptor and no unused receive address, or a change descriptor with no `[fingerprint/path]`. Address-only wallets could not consolidate before either (their inputs have no origin, so the PSBT build refuses). The Coins page shows only the PSBT or the error text, so it needed no change. `plan_consolidation_inner` was split out of the command so the plan can be tested. Limits: nothing was signed with a real signer; the next change address is derived from what sync has seen, so a consolidation that was broadcast but not yet synced makes the next plan derive the same address (plan_spend behaves the same way).
- **A packet's snapshot balance could overflow the portfolio total.** An inheritance packet can carry a last-known balance and coin count per wallet. Both came from the file unchecked and were stored as given. The Portfolio total, and each custody and risk group, then added the balances with plain `+=`, so two wallets near `i64::MAX` panicked in a debug build and wrapped to a negative total in a release build (the release profile does not check overflow). Found in a read-only code review; not reproduced in the app. Now:
  - Import skips a packet wallet whose snapshot balance is outside 0 to 21,000,000 BTC (2,100,000,000,000,000 sats) or whose coin count is outside 0 to 10,000,000. The wallet is reported with a reason ("the packet's last-known balance is not a possible amount..."), nothing is written for it, and the other wallets still import. The same skip-and-report pattern as the key-like text check.
  - Reading ignores a snapshot outside that range (balances, the Portfolio total and the "snapshot wallets" list), so a database that already holds one from an earlier import is covered too. No migration.
  - The Portfolio total and the per-custody and per-risk sums are checked: a sum that does not fit is an error ("wallet balances are too large to add up"), not a panic or a negative number. This also covers `manual_balance_sats`, which is user-entered and still not range-checked at entry.
  - The upper bound is below 2^53, so a valid balance survives the trip through JavaScript numbers.
- **Explorer lookups froze the window, and the fee fallback could abort the app.** Two findings from a read-only code review and the check that followed. (1) `get_explorer_height` and `explorer_lookup_address` were synchronous commands, which Tauri runs on the main thread, so with the explorer on and the server slow or unreachable the window froze for up to the 8 s timeout; the Node page calls `getExplorerHeight` when it opens. (2) Found while fixing that: the explorer's HTTP client (`reqwest::blocking`) panics when it runs or is dropped on a thread that belongs to an async runtime ("Cannot drop a runtime in a context where blocking is not allowed"; reproduced with a loopback test). `get_fee_estimates` has been `async` since the TLS and blocking fix above, and its explorer fee fallback calls that client, so with the explorer on and no estimates from Core or Electrum the fallback would have panicked; with the release profile's `panic = "abort"` that ends the app. No earlier test enabled the explorer in that path. Now:
  - `ReqwestHttp::get` runs each request on a fresh OS thread of its own and waits for it (at most the existing 8 s timeout), which is safe from any caller, sync or async. This fixes the fee fallback.
  - `get_explorer_height` and `explorer_lookup_address` are `async`. The saved settings are read inline (database and vault only) and the request itself runs on a blocking-pool thread (`tokio::task::spawn_blocking`), so neither the window nor an async worker waits. Failures still come back as data (the height) or an error string (the lookup).
  - No UI change: the frontend already awaited both. The explorer client, the 8 s timeout, the redirect limit and the explorer being off by default are unchanged.
  - Still true: `get_fee_estimates` waits on its request while holding an async worker, as it already does for Core and Electrum; `sync_wallet` and other commands that do network I/O were not changed.
- **Key and passphrase hygiene: the vault key's copies were only partly wiped.** Found in a read-only code review. `derive_key` built the Argon2id output as a PHC hash object and copied it into a local array and then into the `MasterKey`; it wiped only a `to_vec()` copy of the hash, so the hash object and the local array stayed in memory. `require_key` (backup export and the older-format restore) copied the key through a temporary. The AES key schedule built for every encrypt and decrypt, and Argon2's 19 MiB working memory (whose last block the key is hashed from), were never wiped, because the crates' `zeroize` features were off. Passphrase `String`s were never wiped. Now:
  - `derive_key` writes the key straight into its `MasterKey`, with no PHC object and no second array, using Argon2's `hash_password_into_with_memory` with working memory that Nakos owns and wipes over its whole capacity before returning. The salt decoding, algorithm, version and costs are unchanged, so every existing vault derives the same key; known-answer vectors recorded from the old code (production cost, a multibyte passphrase, four lanes) are pinned by a test.
  - The `zeroize` features of `argon2`, `aes-gcm` and `aes` are on (`aes` is named directly in `Cargo.toml` only to switch its feature on). `Cargo.lock` gains dependency edges to `zeroize` and no new crates. The AES key schedule is now wiped when the cipher is dropped.
  - `require_key` copies the vault key straight into a heap box (no stack temporary) that is wiped on drop.
  - The passphrase `String` that arrives over IPC is wrapped in `Zeroizing<String>` as the first step of `vault_init`, `vault_unlock`, `set_keychain_helper` and `restore_encrypted_backup`, and `keychain_load_passphrase` returns a `Zeroizing` value, so each is wiped on every return path.
  - Not fixed, and not claimable: the returned `MasterKey` is still moved by value, so a 32-byte copy can remain on the stack; the passphrase text is created by Tauri's IPC and serde before Nakos's code runs, and JavaScript strings in the webview cannot be wiped; there is no `mlock`, so the key or other memory can still reach swap, a hibernation file or a crash dump; locking drops and wipes the key struct but does not scrub the whole process. "Zeroed on drop" in `docs/THREAT_MODEL.md` is true of the key struct, the Argon2 working memory and the AES key schedule, not of the whole process.
- **The Fragmentation planner ignored the fee when choosing coins.** In the Spending Planner, the Fragmentation option (smallest coins first, to clear dust) took coins until their total reached the send amount, with no allowance for the fee. When the smallest coins just covered the amount, planning failed later with "selected inputs can't cover amount plus fee — lower the amount or fee rate", although adding one more coin would have worked. The Fee, Privacy and Lowest-tax options already counted the fee. Found in a read-only code review. Now Fragmentation uses a new pure function, `coin_select::select_smallest_first`: smallest coins first (ties by id, so the choice is deterministic), taking coins until amount plus the fee they add is covered, using the same fee estimate as the other options; if even all coins together cannot cover it, the plan says "insufficient spendable (unfrozen) balance in this wallet to cover amount plus fee". The coins are still taken smallest first, so the option still clears dust. No UI change. Limits: the estimate is the same per-script size heuristic the other options use, so if it ever underestimates a wallet's real input size the later exact check can still say "can't cover amount plus fee" (that applies to all four options and was not changed); smallest-first can still take tiny coins that cost more in fee than they carry, which at high fee rates is wasteful but is what the option means.
- **A compromised webview could name any file path for backups, letters and the Core cookie.** Found in a read-only code review; needs a compromised webview (for example a malicious npm dependency), so low severity. Four commands (`export_encrypted_backup`, `restore_encrypted_backup`, `export_inheritance_packet`, `import_inheritance_packet`) took a file path as an argument from the frontend, which had picked it in its own dialog; nothing in Rust could check that. A webview could overwrite any user-writable file with backup or letter bytes, or have a file read in. Separately, Bitcoin Core's cookie file was read by the RPC library, which sends the first line of whatever file the saved path points at as Basic auth: a path pointed at some other file, paired with a hostile host, would have sent that line. Now:
  - Rust opens the native dialogs itself (`commands/file_dialog.rs`, via `tauri-plugin-dialog`), so the webview never names a path. The encrypted backup export, the packet export and the packet import are single commands with no path argument that return the path written (or nothing if cancelled). Restore keeps its two screens: `pick_backup_to_restore` opens the dialog and remembers the file in the app state, and `restore_encrypted_backup(passphrase)` reads only that file; it stays until a restore succeeds, so a wrong passphrase can be retried without choosing again, and without a remembered file the command says "choose a backup file first". The export checks that the vault is unlocked before showing the dialog.
  - Nakos reads the Core cookie file itself and accepts only Core's real cookie: one line, `__cookie__:` then 64 hex characters, from a regular file read through a 256-byte cap. Any other file, a directory, or a named pipe (which would block forever) is refused, and the error never contains what the file held. The RPC library no longer reads the file, so no other file's contents can reach the wire.
  - The webview's dialog permission is narrowed from `dialog:default` plus `dialog:allow-save` to `dialog:allow-ask` (the archive confirmation) and `dialog:allow-open` (the cookie file Browse button); the message and confirm dialogs, which the app does not use, are no longer granted.
  - The Settings backup export, the command palette's letter export, the packet export and import, and the restore dialog now make single calls with no path. The cookie Browse button still picks a path in the webview, which is saved as text; only what is read from it is restricted.
  - Not covered: the saved cookie path can still be any text (only its contents are restricted); a cookie from a node other than Bitcoin Core (for example btcd) is now refused; display strings such as the path shown after an export are not security-relevant.
